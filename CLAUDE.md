# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Rep Pilot ("REPILOT") — a workout/fitness log and coach for iOS, with an Apple Watch companion for live in-workout logging. SwiftUI + SwiftData, iOS 17+ / watchOS 10+. Fully local-first: no accounts, no backend — all data lives on-device via SwiftData, with Apple Health as the only external integration.

## Commands

Project files are generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` — **run `xcodegen generate` after editing `project.yml` or after adding/removing any source file**; the `.xcodeproj` is a build artifact, not a source of truth.

```sh
xcodegen generate

# Build
xcodebuild -scheme RepPilot -destination 'generic/platform=iOS Simulator' build
xcodebuild -scheme RepPilotWatch -destination 'generic/platform=watchOS Simulator' build

# Run on a specific booted simulator (replace with a real device UDID from `xcrun simctl list devices`)
xcodebuild -scheme RepPilot -destination 'id=<SIMULATOR_UDID>' build
```

`xcodebuild test` currently fails for `RepPilotTests`/`RepPilotUITests` with "Cannot code sign because the target does not have an Info.plist file" — this is a pre-existing toolchain mismatch (`project.yml` pins `xcodeVersion: "16.2"`, but the dev machine may run a newer Xcode, which changes `GENERATE_INFOPLIST_FILE` defaults), not something introduced by app changes. Both test targets are currently empty boilerplate (no real tests written yet).

## Architecture

### Two targets, one shared payload

- **`RepPilot/`** — the iOS app.
- **`RepPilotWatch/`** — the watchOS companion. Runs independently of the phone (`WKRunsIndependentlyOfCompanionApp: true` in `project.yml`) — it can record a full workout with no phone nearby.
- **`RepPilot/Shared/`** — compiled into *both* targets (see `project.yml`'s `RepPilotWatch.sources`): `WatchWorkoutPayload.swift` (the wire format sent watch→phone) and `WorkoutTypeCatalog.swift` (the 25 selectable workout types, each mapping a display name to an `HKWorkoutActivityType` + `HKWorkoutSessionLocationType`).
- `RepPilot/Models/ExerciseLibrary.swift` is also compiled into the watch target directly (listed explicitly in `project.yml`, not via the `Shared/` folder).

### Watch ↔ phone sync

Sync goes over `WatchConnectivity`'s `transferUserInfo` (not `sendMessage` — it's queued/durable, doesn't need the other side reachable at send time). Both sides layer their own retry queue on top since `transferUserInfo` only guarantees eventual *delivery*, not that the receiver successfully *processes* the payload:

- **Watch → phone**: `RepPilotWatch/Services/WatchOutboxStore.swift` persists outgoing payloads until `WCSessionDelegate.session(_:didFinish:error:)` confirms delivery; `WatchConnectivityService` retries the outbox on reachability changes and app foreground.
- **Phone-side import**: `Services/Connectivity/PhoneConnectivityService.swift` receives the payload, `WatchWorkoutImporter.swift` reconstructs it into `WorkoutSession`/`WeightExerciseTypeLog`/`SetEntry`, deduped by the payload's `id` against `WorkoutSession.watchImportID` (so redelivery never creates duplicate workouts). `PendingWatchWorkoutStore.swift` queues anything that arrives before the phone's `ModelContext` is ready (e.g. a cold background launch) and retries on next foreground/reachability change.
- `WorkoutHealthEnrichment.swift` separately polls Apple Health for the richer HealthKit record (heart rate, calories, route) once the watch's `HKWorkoutSession` has finished writing it — this can lag behind the WatchConnectivity payload by a few seconds, so a freshly-imported watch workout may briefly show zeroed stats before enrichment fills them in.

### SwiftData schema versioning

`Services/Migrations/SchemaV1.swift` — **never modify this file once real user data exists on it.** To change any `@Model` type's fields: create `SchemaVN+1.swift` (see the doc comment in `AppMigrationPlan.swift` for the exact pattern — lightweight vs. custom migration stages), add it to `AppMigrationPlan.schemas`/`stages`, and **also bump `RepPilotApp.swift`'s `Schema(versionedSchema: SchemaV1.self)`** to the new version — this second step is easy to miss and isn't mentioned in `AppMigrationPlan.swift`'s own instructions, but the migration plan is inert without it.

### Workout type → activity type resolution

`ActivityTypeMapper.swift` (phone-only) is the canonical list of activity names and their cardio/strength/mobility scoring profiles, seeded into the `ActivityType` SwiftData model by `DatabaseSeeder.swift` on first launch. The watch's `WorkoutTypeCatalog` (in `Shared/`) is a *curated subset* of these names, chosen so every watch-startable type also has a matching case in `HealthKitService`'s `HKWorkoutActivityType → name` mapping — keeping the name strings in sync across all three (`ActivityTypeMapper`, `WorkoutTypeCatalog`, `HealthKitService`) is what makes a workout started on the watch resolve to the correct `ActivityType` (and correct cardio/strength/mobility scores) once imported on the phone.

### GPS / location

Only these `WorkoutTypeCatalog` entries use `HKWorkoutSessionLocationType.outdoor` (GPS route recording): Running, Cycling, Walking, Hiking, Dancing. Everything else is `.indoor`. This is what `NSLocationWhenInUseUsageDescription` (watch-only entitlement/Info.plist key in `project.yml`) is for — the phone target has no location usage.

### Coaching

`Services/Coaching/` — `CoachingService` is a protocol; `RuleBasedCoachingService` is the current (offline, no-ML) implementation. `CoachingModels.swift` holds the shared request/response types.
